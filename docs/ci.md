# CI checks

CI starts on every pull request to `master`, push to `master`, and manual dispatch. It selects checks before Python setup or dependency installation. It does not use workflow path filters: a skipped workflow can leave a required check pending. CodeQL continues to perform its actual Python scan independently on every existing trigger.

The selector compares the complete event base with the tested commit. Pull requests use the checked-out merge tree and require that the advertised base is its ancestor; pushes use `before`. Both rename paths and deletions are retained using NUL-delimited Git records. Missing commits, malformed event/diff data, unknown paths, Git failures, and manual dispatch select everything. Selection publication failure makes the job fail. Mixed changes union their dependencies.

The map includes lazy imports from MCP into adapters, the real broker restarted under a running adapter by the reconnect contract, the diagnostic trace written by the MCP frontend and native RPC and bundled by the CLI, public CLI dispatch, the real stdio subprocess in end-to-end/behavior tests, native RPC fixtures used by behavior, and broker inputs consumed by the performance driver, including the `xordination serve` path it starts as a separate broker process. The live_acceptance group runs deterministic evidence-validator, held-request and passive-observer tests, and feeds a report retained by `live.py verify` through `xordination readiness`, so the live.py producer and the readiness consumer each select that edge (live.py also imports its source fingerprint from readiness, so readiness changes select every live group); live_native_busy exercises actual adapter/observer/broker orchestration with owned scripted native executables. Its passing control starts an idle recipient, primes a real unfinished native request, submits the correlated pair only after readiness, then verifies receipt/reply handling after release. Its planted no-readiness red requires the exact failure stage. The dedicated immutable native fixture selects only that group. live_tmux drives the managed launcher's supervisor through a subprocess stand-in for tmux, a real broker started through the launcher's broker window (the same `xordination.cli.serve` path as `xordination serve`) and scripted native participants; it requires no tmux installation. Real tmux command parsing is checked by the launcher's `self-check` on a private socket, outside CI. Selection never launches a paid native session. A full selection discovers every `test*.py`, including new modules. An absent or empty registered selected module is an error. Update the map when dependencies change; uncertainty should retain the full fallback.

Every selected case is required. The runner reports collected cases, starts, actual execution, skipped cases and unexercised cases separately. Required skips, fixture failures that prevent case execution, and `expectedFailure` markers fail the check. Intentional fault probes must assert the intended failure reason within an otherwise passing test. The canonical coverage artifact retains `test-execution.json`; other matrix jobs retain their census in the job summary.

Jobs run fast checks first and stop early. `lint` and `fast` start together. `fast` selects the checks, then runs the in-process groups (store, mcp, server, cli, ci_selection; about a hundred cases in seconds) on Python 3.12 under coverage. The `contracts` matrix and the `package` job start only after both pass, so a lint error or a fast contract failure spends no further runner time. `contracts` runs on Python 3.10, 3.12 and 3.14 with matrix fail-fast, so one interpreter's failure cancels the others. Python 3.12 runs the remaining slow groups; 3.10 and 3.14 run every selected case. Each job runs its cases as three parallel shards (adapters; live_tmux with live_native_busy; live_acceptance, behavior, end_to_end and performance), balanced by measured duration, in their own process groups. The first failing shard stops the rest, and their cases are reported as not run, so the job still fails. Test modules outside the registered groups join the last shard. The 3.10 and 3.14 jobs also validate source imports through the public CLI; they do not rebuild or install the wheel. `CI result` aggregates every job: a selected job that failed, was cancelled or never ran fails it. The ruleset currently requires only the lint check.

The `package` job runs in parallel with `contracts` on Python 3.12. It builds one source archive, checks its included runtime/docs/tests/CI inputs, rebuilds a wheel from that archive, checks license notices, and exercises a fresh installation outside the checkout. The installed smoke explicitly rejects checkout imports and checks send/inbox/ack/status behavior, and the installed `xordination readiness` must pass the package level. The image check then installs that wheel, and the benchmark runs last. Only the benchmark checks out full history, to read the base commit.

Python 3.12 measures the fast tier in the `fast` job and the slow shards in `contracts`. Shard and subprocess data are combined with the fast tier's data into one branch/thread/subprocess coverage report, `coverage-python-3.12`; `coverage-fast` keeps the fast tier alone. A contract may SIGKILL a stubborn fixture process while it saves coverage; such partial data files are set aside and listed in `baseline.json` rather than failing the report. Each report names the selected groups and whether it is full; partial reports are not whole-suite regressions. Manual dispatch refreshes the full baseline. See [coverage baseline](coverage-baseline.md) for measured gaps and process limitations. Coverage is a development-only `ci` extra; runtime dependencies stay empty. There is no percentage threshold. Source-archive checks retain the shared fixtures and both CI/testing drivers so a packaged source checkout can reproduce the tests.

Selected broker/benchmark inputs also run a small, uninstrumented performance measurement on Python 3.12. `benchmark_compare.py` extracts only the event base's regular product-source files and runs the current benchmark and shared helper against both base and head on the same runner. It does not execute the base's test/CI scripts. Both revisions use one shared measurement-session identifier, 8 work units per peer, 4 concurrent peers, 3 measured trials and 1 discarded warmup per scenario, with seed 0 and 256-byte payloads. The driver validates actual product imports and comparable configuration/driver/environment identities. Reports include correctness, sample counts, API p50/p95, workload-specific throughput, lifecycle timings and retained storage. Two additional separate-broker-process trials report broker CPU/RSS, wait capacity and restart recovery; together they add a few seconds per revision. These are authenticated loopback HTTP measurements, not isolated broker execution, native receipt or model-response latency.

Timing comparisons are report-only; head workload correctness failures still fail CI. `performance-python-3.12` retains the produced reports, comparison and CI context, including source hashes and the full event base/head identities. A missing/unavailable product baseline is explicitly head-only with no comparison, never an inferred improvement. A failing historical baseline retains its failed evidence and exit status while the required head measurement still runs; it cannot authorize a timing comparison or block a PR that fixes that correctness failure. The fixed base-then-head ordering and small samples can contain host/order effects; establish repeated-run variance before adding a performance budget. Manual dispatch accepts bounded message/trial/worker counts (1–128, 2–12, 1–16) and an optional complete baseline commit SHA; without that SHA it reports head-only. It still runs the full contract/package/image checks.

The image check builds the broker, verifies UID 10001, bootstraps a named state volume, rejects an invalid token, sends an idempotent message, records an acknowledgement and reply, then replaces the container and checks retained state. Its cross-profile check (AC-14) installs the package step's wheel from `dist/` into a fresh host environment: that installed client's `readiness` must pass the service level against the published container endpoint, its message must reach a client running inside the container, and the container-side receipt must be visible to the host client before and after replacement. Every image selection therefore also selects the package step. `tests/test_end_to_end.py` checks the same sharing locally with a separately launched broker process, bootstrap and isolated client processes, and a broker restart. Its port is bound to host loopback. Cleanup removes only its UUID-named container/volume, including on failure; it does not publish, authenticate to a registry, or prune global resources.

The Python 3.12 jobs cache pip downloads using `pyproject.toml`, which declares the build and coverage dependencies. The lint job installs its pinned tools uncached, so it cannot claim that cache key. `scripts/ci/install.py` installs any pinned set by name (`lint`, `ci`, `build`), and `scripts/ci/report.py` writes job summaries, so the workflow repeats neither. Installation still runs each time; the cache is not an installed environment. No external Docker cache is configured. Shards run inside a job rather than as separate jobs, because each extra job would repeat checkout and Python setup, which costs more than the shard it runs. Existing concurrency cancellation drops obsolete runs for the same workflow/ref.

The lint job runs on every trigger without selection; it needs no product import and takes seconds. Ruff checks Python with correctness rules (`E4`, `E7`, `E9`, `F` and bugbear `B`) plus a selected set of flake8-bandit `S` rules for patterns never intended here (`exec`/`eval`, pickle/marshal, `shell=True`, unsafe YAML, disabled TLS verification, weak hashes, binding all interfaces, SQL string building), targeting Python 3.10 and configured in `pyproject.toml`; it applies no style, import-order or formatting rules. The broader Bandit-style rules (`subprocess` without a shell, `try`/`except`/`pass`) describe intended patterns in this code base and stay off; CodeQL performs the data-flow security scan. `scripts/ci/lint_checks.py` runs the pinned Ruff with the repository configuration over an unsafe and a safe sample for every selected `S` rule: each rule must report its unsafe sample and stay silent on the safe one, and a selected rule without samples (or samples without a selected rule) fails, so a Ruff upgrade cannot silently drop a check. ShellCheck checks every tracked `*.sh`/`*.bash` file, and actionlint validates the workflows and runs the same ShellCheck over each `run:` step. Shell embedded in the Dockerfile is not linted. The tools are pinned in the development-only `lint` extra (with the `tomli` backport on Python 3.10, so the calibration also runs there), separate from the `ci` coverage extra; runtime dependencies stay empty. Suppress a finding inline with its rule code only when the reported pattern is intended, for example a lambda that runs within its own loop iteration.

For a full local check:

```sh
python -m pip install '.[lint]'
ruff check .
python scripts/ci/lint_checks.py
git ls-files -z -- '*.sh' '*.bash' | xargs -0 --no-run-if-empty shellcheck
actionlint -shellcheck "$(command -v shellcheck)"
python scripts/ci/select_checks.py --event workflow_dispatch --selection-file /tmp/xordination-selection.json
PYTHONPATH=src python scripts/ci/run_contracts.py --selection /tmp/xordination-selection.json --tier fast
PYTHONPATH=src python scripts/ci/run_contracts.py --selection /tmp/xordination-selection.json --tier slow --parallel
python -m pip install '.[ci]'
PYTHONPATH=src python scripts/ci/coverage_baseline.py --selection /tmp/xordination-selection.json --output /tmp/xordination-coverage
python scripts/ci/check_package.py
docker build --tag xordination-ci .
python scripts/ci/image_smoke.py --image xordination-ci --dist dist
python scripts/testing/benchmark.py --messages 8 --workers 4 --trials 3 --warmup 1 --output /tmp/xordination-performance.json
```

The coverage command is an alternative measurement run, not a required second test execution. `check_package.py` requires the declared build-system tools installed. Image execution requires Docker and remains verified by the hosted CI run when Docker is unavailable locally.
